Design Tokens Pro vs the DTCG spec

The Design Tokens Community Group publishes the interchange format for design tokens. The stable Design Tokens Format Module 2025.10 describes JSON files with $value, $type, and $description, plus groups, aliases, and typed values (color, dimension, typography, shadow, and more). Tools such as Style Dictionary, Tokens Studio, Figma, Penpot, and Sketch are aligning to it.

A specification is a contract between tools. It is not a playbook for a product team. That gap is where Design Tokens Pro sits.

What the spec decides

The DTCG format tells vendors how to serialize a token so another tool can read it. It defines types, how references work, and how groups nest. It deliberately does not prescribe your taxonomy (“always use color.bg.primary”), your number of layers, or how you run a design system. That restraint is correct for a standard: if the spec mandated names, it would freeze every brand into one vocabulary.

Reading the spec is worthwhile if you ship a tool, write a transformer, or need to choose between legacy JSON and DTCG JSON. It is slow going if you are a designer trying to name a spacing scale this afternoon.

What the guide decides with you

Design Tokens Pro is a practical written guide ($39) on the human and product choices the spec leaves open:

  • How to build a shared vocabulary and naming convention
  • Which parts of a token name carry meaning — category, property, purpose, scale
  • How to architect primitive, semantic, and component tokens
  • How compound tokens, themes, and color modes stay maintainable
  • How to document tokens and manage their lifecycle across tools

The examples are JSON you can map onto DTCG fields. The guide does not replace 2025.10; it makes you ready to fill a valid file with decisions your team can live with.

Read both, in this order

If you are new to tokens, start with the guide (or the two free chapters). You will know what a token is for, how names encode decisions, and why aliases exist. Then skim the spec so your files can move between Figma, code, and documentation tools without a one-off converter forever.

If you already emit DTCG JSON and still have inconsistent names, duplicate themes, or tokens nobody dares to delete, the spec has already done its job. The remaining work is process and architecture — that is the guide.
